值得关注的研究和论文#

The Tasteful Agent: Measuring and Improving Taste in Long-Horizon Tasks#

arXiv:2609.25804

把 Agent 的 taste 操作化为“在尚未看到后续结果时，能否选对技术方向”：从既有运行轨迹挖掘决策分叉，隐藏后续结果测试判断力，再将拥有结果信息的教师推理蒸馏给学生。

从运行轨迹构造判断题

最终成功率混合了路线选择、执行质量与环境因素。Taste-Bench 将评测截在具体分叉处，只提供任务、分叉前历史和两个候选方向，要求模型提前选择。

  • Parallel：配对同一任务的成功与失败尝试，定位两条轨迹选择不同方向的位置。
  • Detour：从单条轨迹提取“走错 → 观察到失败 → 改换方向 → 成功”，把题目放在首次走错之前。
  • 过滤：剔除仅看候选措辞就容易猜中的题，以及完整后续记录仍不能支持标签的题；4,657 个候选最终保留 502 题，其中工程题 390 道、研究题 112 道。

每题交换选项顺序评估两次，只有两次都答对才计分；headline 分数为工程与研究严格准确率的等权平均。因此，两次独立随机猜测的基线为 25%，不能直接与普通二选一准确率混用。（§3、附录A/C）

特权上下文蒸馏

教师与学生使用相同的 Qwen3.6-27B 基座，教师额外知道正确方向，学生只见决策当时的信息。教师生成推理与最终选择，在教师续写序列上计算 token-level KL，训练学生的 LoRA；随后让学生自由推理，以真实标签对最终答案位置做 cross-entropy 校准。390 道工程题按任务分为两折，分别训练、交叉评估。（§5.1、附录G）

在执行实验中，学生把每个分叉转为“适用情境—避免方向—建议方向”的短建议，提前放入固定执行器的任务上下文，并要求执行器自行测试验证。

Follow the Entities: A Corpus Map for Agentic Search#

arXiv:2609.37226

CorpusMap 将跨文档反复出现的实体整理成可复用的语料地图，让 Agent 沿实体页找到互补证据，减少每次查询都重新发现文档关系的开销。

核心方法：实体身份约束的导航层

传统原文搜索容易漏掉措辞不同、分散在多个来源中的证据。CorpusMap 在保留全部原文的同时，建立实体—文档二部图：一篇文档可以属于多个实体邻域，未关联实体的文档仍可直接搜索；默认不增加显式实体—实体关系边。（§3.1–3.2）

离线构建分为四步：

  1. Cataloging：从样本文档归纳实体类型目录，为每类对象定义身份判别规则和原文例子，随后固定目录。
  2. Extraction：逐文档抽取实体，把同一对象在该文档内的不同名称合并，名称须来自原文。
  3. Resolution：对照共享 registry 做跨文档消歧，以 LINK 关联现有对象、ADD 新建对象，证据不足时保留 UNRESOLVED。
  4. Rendering：仅为关联至少两份文档的实体生成 Entity Page，汇总别名、概览、带来源的关键事实和原文路径。（§3.3，算法1）

查询时先用 BM25 检索相关实体页，汇总其关联文档，再按标题和内容重排，给 Agent 候选文档的标题、路径与 ID。Agent 可继续用 shell 搜索实体页和原文、沿链接补证据，候选入口不会限制可访问范围。（§3.4，附录B.3）

GitSwarm: Decentralized Compounding Inference#

arXiv:2610.04862

将多轮推理留下的代码、实验、失败与验证证据组织成可分支、可追溯的成果图，让后续 Agent 能检查、接力和组合已有工作，形成跨 episode 的 compounding inference；模型权重保持固定，持续演化的是外部工作状态。

核心设计：贡献、分支与语义依赖

共享 Git 仓库同时承担三种职责：用不可变 commit 持久保存成果，用分支保留竞争路线，用显式依赖记录跨路线借鉴。

一个贡献有两种来源关系：物理父节点表示继承哪棵文件树，informed_by 则列出实际依赖的先前贡献，且必须包含父节点。因此，worker 可以从 A 的实现继续开发，同时引用 B 分支发现的反例，而无需先合并两个分支。语义边记录声明的影响关系，不代表自动代码合并或因果贡献归因。（§2.1–2.2）

worker 如何协作

  1. 在隔离 worktree 中查看历史与在途工作，自主选择起点和下一步，公开工作范围。
  2. 一次 episode 可以贡献一个原子 commit、提名已有候选，或因重复和缺少收益而主动退出。
  3. 每个贡献保留 MY_THOUGHTS.md 与 EVALUATION.md，记录假设、来源使用方式、实际检查、不确定性和下一步；分析或失败实验也须继承一个满足任务结构要求的候选。
  4. 解题任务按精确候选 SHA 的有效提名数选出最终版本；架构研究按验证指标选择，不采用投票。

dashboard 和活动日志用于发现正在进行的工作；未提交内容须落成 commit、经过检查并被引用，才可作为持久来源。中央 harness 仍负责调度、校验和发布，“去中心化”主要体现为 worker 自主选择工作；发布校验通过不等于答案正确。（§2.3–2.5、附录 H）

DiscoveryRSI: Recursively Learning to Discover Valuable Hypotheses#

arXiv:2610.23839

将科研提案的版本演化、证据与 Agent 行动连接起来，通过贡献加权微调和研究工作流回放，让系统从已有研究经历中学习如何提出更可检验的假设

把假设定义成可检验的研究对象

论文将假设表示为 $H=(c,\pi,d,a)$：主张、调查计划、判断标准和替代解释。每个对象还绑定证据与资源约束，在获得结果前就说明什么观察支持、削弱或仍不足以区分主张。一个脚本执行成功、一个提案获得高分、一个科学结论被独立证实，分别记录。

系统维护三类相互关联的记录：

  • 假设发展图：保存版本、修订与多父节点组合，描述科研内容怎样演化，实际可以是 DAG
  • Agent 调用轨迹：保存指令、动作和工具观察，用于定位可以监督的响应与工具参数
  • 贡献与证据关系：通过发布记录、草稿、文件哈希和执行依赖，将评价连接到有依据的参与记录

共享同一材料不自动构成假设祖先关系，出现在同一研究轮次也不自动获得训练 credit。（§2–3；附录 A/B）

内层搜索与外层学习

Lead 选择研究方向，Generation/Evolution 生成、修复或组合提案；Critique 隐去模型身份比较方案，Progress 对照祖先判断实质进步、必要修复、重复或证据不足。Compiler 将入选计算计划封装为带输入、环境、输出和验证条件的 Harbor 任务。

外层包含三条机制：

  1. Hypothesis Credit Optimization：根据提案评价与贡献记录分配 credit，施加限额后再计算训练权重
  2. Harness Replay：固定模型，从失败轨迹诊断协调、工具、证据访问与完成检查的问题，再回放比较工作流修改
  3. Rediscovery：将开发集接受的模型与工作流更新用于新问题，采集下一轮研究经历

DFM-Bench 分别评价单个假设、一次修订、发展路径、整轮研究与去重后的科学贡献；任务交付成熟度另记，整轮研究分数也不由路径均分代替。（§3–4；算法 1）

Automation and Repression#

Daron Acemoglu、A. Arda Gitmez 与 Mehdi Shadmehr 在这篇 2026 年 6 月的理论论文中，将自动化放进政治经济学框架：当国家代表资本所有者、劳动者可能反抗时，限制自动化、再分配与镇压之间会形成怎样的权衡？文章提供了理解技术选择与收入分配关系的一种机制，其结论依赖模型中的政治与成本假设。

More automation requires more redistribution in order to counterbalance the unequalizing effects of automation.

The Next Era of Knowledge Work#

OpenAI 在这份 2026 年 6 月报告中，从搜索、协调、审批与验证三类摩擦切入，结合 Codex 的使用数据和案例，讨论 Agent 如何将跨工具、碎片化的知识工作组织为可并行、可检查的工作流。值得关注的是围绕 Agent 重构流程、分工与验证机制的思路；报告中的平台数据与案例尚不足以单独证明普遍的生产率收益。

The user becomes the orchestrator of workstreams rather than executing a single task at a time.

企业的未来#

Hemanth Asirvatham 与 Elliott Mokski 从 AI 成为下属、同事或协调中间层三种情景出发，讨论人机混合型企业如何改变员工自主权、企业规模和薪酬差距。这篇代表作者个人观点的文章，把问题推进到组织与权力如何重排；不同走向取决于需求增长、监督方式，以及人类仍能提供的价值。

LLMs are making formal software verification feasible at a much larger scale#

Anthropic 与 Theorem 将既有 fuzz tests 转为形式化规格，由 Claude 生成证明、Rocq 核验，在 123 个开源库的 239 个测试入口上验证特定条件下的无崩溃性质。文章展示了从测试走向可检查证明的工程路径，也交代了结论的适用范围：所建模的单线程静态 RISC-V/Linux 环境，以及小于 64 MB 的输入。

“Formally verified” does not mean “bug-free.”

前线部署工程在 OpenAI 意味着什么#

OpenAI 前线部署工程负责人 Colin Jarvis 结合客户案例，解释 FDE 如何弥合模型能力与生产可用性之间的鸿沟：先围绕业务结果构建和评估系统，再把有效流程沉淀为通用能力、Skills 与插件，并将能力缺口反馈给研究团队。值得关注的是，如何让一次定制成为下一次部署的起点。

我们的目标是让每一次合作都为下一位客户留下更好的起点。

How to Be More Ambitious: A Tutorial for Humans With Models#

I think of ambition in four types: Speed, Altitude, Depth, and Range.

Speed: The same work in less time, the bread and butter for AI’s economic value

Altitude: Going up in abstraction and considering the outcome rather than the individual task.

Depth: Considering a task the way a field-leading expert would.

• Range: Drawing on multiple fields rather than just the one the task might need at the surface, using knowledge, tools, and techniques you normally wouldn’t.

Building Agents: When to Fold Subagents Into Your Main Agent Loop#

one clear system prompt, 4-5 thin data tools, and firm output guardrails would cover most of the use case.

To be clear, subagents still have their place, including at the research frontier. Use them when:

Companies often want to build an agent that unites multiple products and capabilities into a single customer interface.

Every team ships its own subagent, so companies end up with hundreds of overlapping subagents with no enforced standards and no specific owner.

The Frankenprompt: Every team adds a sentence to the system prompt, resulting in conflicting rules and no consistent voice.

but often a more effective approach can be progressively disclosing context via skills and progressively disclosing tools via tool search.

Knowledge bases are the right fit for reference material the agent only needs some of the time.

Personal Agent是个很移动互联网的事#

我理解，美国投资人都在抢一样东西：AI to C的话语权。

而 Personal Agent 则提供了另一种解法：模型层逐渐降低成本和对最先进模型的依赖，但用户关系、使用习惯，以及交易前面的位置，可以留在应用公司手中。

先回答一个很普遍的问题：Muse 能做的事，OpenClaw 不早就能做了吗？

Muse 做的一个关键步骤，是把自行部署维护，变成云端托管、注册即用。用户不必先成为半个工程师，才能拥有一个替自己办事的 Agent 。

因为AI办公产品从第一天起，就不是围绕普通人的生活来设计的。办公 Agent 的记忆和上下文可以围绕项目和任务构建，但一个普通人的日常里哪有那么多值得“专门立项”的任务？

它们可能不值得专门打开一个工作台，却最好能有个什么东西一直替你盯着。

用 Manus 改造 Manus，AI Native 组织改造的实践和思考#

人亲手执行的部分越来越少；指挥 AI 干活、为 AI 的工作结果承担责任占的比重越来越大。

组织方式、人与 AI 的关系，信息流动，每个人的能力边界，都在不知不觉中被调整，甚至是重塑。

最大的损耗在联调。

探索 AI 的使用边界本来就是我们的追求。

团队无法忍受低效。

组织足够扁平。这使得大部分决策，不管是自上而下，还是自下而上，都能快速覆盖到整个组织。

这个链路上的人很多，信息每经过一个人就会丢一点。同一份需求文档，产品和设计做出的原型可能完全不同。

很多以前要“找人问”的事，现在不必打断那个人了。在 Manus 内部，我们逐渐形成了一些共识

我们做了一个目前只在内部使用的协作功能：同一项目的成员默认能看到彼此的 Session，也可以申请进入对话发言。

这笔钱买的不是人力，而是时间和注意力

用 AI 省下的是每个人的注意力，让每个人对自己负责的事更有完整的掌控。

贵是因为用最好的模型，这是了解 AI 边界的核心方法

这不只是效率提高了，而是组织运转的方式在改变

在清迈做数字游民，我观察到的东西方文化差异#

后来我慢慢意识到，对于流动性极强的圈层来说，small talk恰恰是社交最有效率的方式之一。它可以让你在新的地方，迅速地让别人对你有一个印象，之后才更容易建立更深的连接。

有一个理论是椰子和水蜜桃文化，椰子文化的人外表是硬的， 看起来好像很不好接触，但是如果你能穿透那个壳，让ta把你当作自己人，那ta会很愿意和你分享深度的东西。

水蜜桃文化则相反，看起来好像和谁都能聊，但实则内心很有距离感。

在东亚文化中，我们更倾向于顺从和附和，谁在这个圈子里最有权威，我们就听ta的，尽管有时内心并不人认可。如果提出反对的意见，很多时候我们会觉得“驳了面子”，容易上升到个人层面。

西方文化并非是没有“驳面子”之说，不同国家的人在做辩论时反驳方式也都有区别
