English version

OpenAI 在 GPT-6 Astra 的发布文章里，专门提到了一项 Codex 的上下文管理变化：模型可以跨窗口保留笔记，更早的窗口仍然可搜索；即使某个需求或测试结果没有写进笔记，后续也可以从历史消息和工具输出中找回来。官方介绍

如果把这件事拆开看，其实涉及两个不同的问题。

第一个是机制：历史存在哪里，怎样移出当前窗口，又通过什么接口恢复。第二个是策略：什么时候应该整理上下文，什么值得保留，什么时候需要回查。

这篇文章从 Codex 的 TokenBudget 路径切入，先看它怎样拆分换窗、笔记和历史查询，再结合 MemexRL、SWE-MeM、CompactionRL 几篇工作，讨论上下文管理如何进入模型的训练过程。

我的判断是，上下文管理正在成为 agent policy 的一部分。 Harness 提供可执行的记忆操作，模型参与决定如何使用这些操作，进而影响自己下一次调用能看到什么。

先区分 context、history 和工作状态#

讨论 compact 时，很容易把“模型当前看不到”和“信息已经丢了”混在一起。

实际上，至少需要区分三层：

层次 存什么 怎样被使用
当前 context 本次调用的指令、消息、工具结果 直接进入模型输入
History 系统保存的会话消息、工具输出与事件 需要相应的查询或恢复入口
工作状态 摘要、笔记、待办、决策与证据索引 帮助恢复进度，并定位需要展开的细节

一条工具输出移出 context，可能仍然保存在会话记录里。但如果模型没有访问入口，或者不知道应该查询什么，这条记录就很难参与后续决策。

因此，上下文管理同时涉及容量和访问。我们需要限制当前输入的规模，也需要给窗口外的信息留下可用的入口。

Agent harness 正好处在这个位置。它负责组织请求、执行工具、保存状态，以及构造下一次模型输入。过去常见的一条路径，就是由 harness 判断何时需要压缩，再调用模型生成摘要。

摘要式 compact 如何重组输入#

OpenAI Cookbook 的 SummarizingSession 是一个清楚的例子。真实用户轮次数超过阈值后，将较早历史总结成摘要，同时原样保留最近若干轮。Cookbook 示例

具体到 messages，较早历史会被替换为一对合成消息：user 要求总结，assistant 承载摘要。下一次输入大致是：

常规指令与请求配置
＋ user：合成的总结请求
＋ assistant：历史摘要
＋ 最近 N 个完整轮次，包含工具调用与结果
＋ 新输入

这里模型已经参与了上下文管理，但主要负责摘要内容。何时触发、处理哪段历史、保留多少近期消息、怎样重新拼接，仍然由程序确定。

此外还有 API 层面的 compaction。Responses API 的 /responses/compact 返回一组可用于后续请求的上下文项，其中包含不透明的加密 compaction item，也可能保留其他输入项。这种压缩状态不能直接等同于人类可读的摘要。Compaction 文档

所以，compact 是一个操作名称，背后可以有不同的实现。比较方案时，需要继续看压缩之后的输入结构，以及被移出内容的访问方式。

摘要保留了进度，但可能遗漏决策依据#

以一个假设的 CSV 导入问题为例。

Agent 经过排查，发现文件开头的 BOM 影响了首列列名匹配，也尝试过一个无效的修复。换窗时，摘要只留下“正在修复 CSV 导入，已完成初步排查，继续检查编码”。

这份摘要保留了方向，但后续模型需要的可能是另外几件事：

  • BOM 在原始输出中具体表现为什么；
  • 哪个方案已经试过，失败原因是什么；
  • 当前判断有哪些测试结果支撑。

如果这些信息没有进入摘要，又没有其他恢复入口，模型就可能重新探索，甚至重复同一次失败。

问题在于，一条信息是否值得保留，往往取决于后续任务。 当下看起来琐碎的错误输出，可能是下一步判断的关键。摘要是否通顺、是否覆盖主要进展，并不足以说明它能支持任务继续执行。

Codex 复盘中的重复压缩问题#

这类风险也出现在实际评测中。2025 年 10 月 31 日，Tibo 与 Codex 团队在《Ghosts in the Codex Machine》的压缩频率一节中写道：

Evals confirmed that performance degrades with the number of /compact or auto-compactions used within a single session.

团队发现，使用压缩的会话占比在逐渐增加，而评测中，同一会话内的压缩次数越多，表现越差。随后落地的改进包括避免多次压缩时的递归摘要，并提醒用户保持会话聚焦。报告原文

这里值得关注的是反复压缩的累积效应。从机制上看，如果下一轮交接依赖上一轮摘要，那么摘要本身就成了下一次信息筛选的输入。某个失败原因在早期被省略之后，后续几轮可能持续在缺少这条信息的状态下推进。

因此，一次 compact 后还能继续执行，只能说明交接完成了，状态保真度需要放到多次换窗后的任务表现中检验。 约束有没有丢失，是否重复探索已失败的路径，都应该成为评估的一部分。

这项观察针对当时的 Codex 实现。报告同时讨论了硬件、工具行为和超时等问题，没有将总体退化归因于单一因素；它给出的改进方向也包括优化摘要机制本身。

沿着这个问题继续看，需要分别验证两个性质：信息是否可恢复，以及 agent 是否会在需要时恢复它。

Codex 的 TokenBudget 路径#

沿着相关 PR 看，Codex 把原来集中在 compact 中的几项职责拆成了独立操作。

new_context 让模型主动请求换窗#

PR #27488 在 TokenBudget 功能开关后加入了直接面向模型的 new_context 工具。

它的执行过程可以概括为：

模型调用 new_context
→ 记录换窗请求
→ 当前采样阶段结束后消费请求
→ 重建初始上下文
→ 在新窗口继续同一轮任务

这条路径不生成交接摘要，也不把旧会话历史自动装回新窗口。模型因此获得了一个新的选择：当它判断当前窗口已经不适合继续工作时，可以主动请求切换。

随后，PR #29743 将 TokenBudget 下的 compact 接到类似的重置路径，使用标准注入上下文开启新窗口，跳过请求服务端总结旧历史的步骤。

这里需要限定范围：讨论的是 TokenBudget 路径，其他配置、模型与压缩入口的行为需要分别判断。

图 1：基于 Cookbook 示例与 Codex TokenBudget 代码快照的机制示意。左侧保留摘要与近期轮次，右侧重建初始上下文。文中图片均可点击查看大图。

notes 保存工作状态，history 提供回查入口#

换窗之后，任务如何继续？

PR #39827 加入了两组直接面向模型的工具：

工具 操作 适合承载的内容
notes 写入、追加、读取、搜索持久笔记 当前目标、决策、待办、证据位置
history 列窗口、列条目、搜索内容、读取条目 先前消息与工具输出中的原始信息

两者的分工比较明确。Notes 负责让模型快速恢复工作状态，history 负责在需要时核对原始材料。笔记可以保持紧凑，详细日志通过查询读回。

前面的 CSV 问题，可能形成这样一条流程：

窗口 A
排查问题
→ 写 notes，保存进度与待办
→ 调用 new_context

窗口 B
读取 notes
→ 判断需要核对之前的失败原因
→ 搜索并读取 history
→ 根据原始输出继续修复

图 2：假设摘要与笔记都省略了 BOM 细节，history 提供了再次读取原始日志的机会。这是示意流程，成功恢复取决于模型的实际选择。

这些工具通过 Codex 后端工作；引入它们的实现要求开启对应配置、使用 OpenAI provider 并具备后端认证。

从机制上看，系统提供了跨窗口延续任务的基础。不过，写笔记和查历史都需要模型采取行动。换窗本身不保证笔记已经写好，记录可查也不保证模型会找到正确条目。

原始证据的可访问性提高了，如何使用证据仍然是策略问题。

从记忆工具到记忆策略#

如果给 agent 一个 notes 和一个 history，它就会管理上下文了吗？

工具定义了可执行的动作，但模型还需要判断这些动作什么时候有用。

更具体地说：

  • 何时整理。 当前子任务是否已经结束？继续保留探索过程是否还有价值？
  • 保留什么。 哪些是稳定结论，哪些是尚未确认的假设，哪些失败原因需要带到下一阶段？
  • 何时回查。 当前状态是否足以支持下一步行动，还是应该先核对原始输出？

这些选择会直接影响后续任务。过早切换可能打断尚未完成的排查，过晚整理可能继续携带大量失效假设；笔记太短会增加恢复成本，笔记不断追加又会形成新的长上下文。

其中最容易被忽略的是回查的触发依据。假如笔记里只有“继续检查编码”，新窗口中的模型怎样意识到自己还缺一条重要的失败记录？

这也是工作笔记需要保留未决问题和证据位置的原因。除了写下结论，还需要留下能够触发后续行动的线索。

从 agent loop 看，任务行动与记忆行动已经进入同一个决策过程：

当前 context ＋ 任务进度 ＋ 预算信息
                  ↓
             模型选择行动
          ↙               ↘
   读代码、运行测试     写笔记、检索、压缩、换窗
          ↘               ↙
       Harness 执行，构造下一次输入
                  ↓
             继续任务

这也带来了一个训练问题：怎样评价一次记忆行动？

写下某条失败原因时，我们还不知道它之后能避免多少次重复尝试。保存一个索引时，也很难只看索引本身判断它有没有用。它的价值，要等后续模型真正需要这份材料时才会显现。

换句话说，记忆操作的收益具有延迟性。要学习这类策略，就需要把后续任务的结果与前面的记忆决策联系起来。

几篇把上下文管理纳入训练的工作#

MemexRL 联合优化经验的保存与读回#

Memex(RL) 的机制是 Indexed Experience Memory：窗口内保留紧凑摘要与索引，详细材料放到外部存储。

它提供两个关键操作：

  • CompressExperience：组织摘要，将详细材料按索引归档；
  • ReadExperience：根据索引读回对应内容。
当前工作上下文
→ CompressExperience
→ 索引摘要留在窗口内，详细材料写入外部存储
→ 后续任务需要某份证据
→ ReadExperience
→ 原始材料重新进入上下文

MemexRL 进一步使用 GRPO 风格的强化学习，将任务行动与记忆读写共同优化。奖励结合任务成功，以及上下文超预算、冗余和格式问题的惩罚。

论文还观察了训练过程中记忆工具的使用变化：压缩调用总体减少，读取调用总体增加。至少在这组实验里，训练改变了模型保存与取回信息的方式。

图 3：MemexRL 的记忆工具使用变化，上图为压缩调用，下图为读取调用。两图来自同一训练实验，横轴为 Rollout Step；调用次数本身不等同于任务质量。来源：Memex(RL)，Figure 5。

它与前面的 notes/history 有相似的机制结构：紧凑状态保留了返回详细材料的入口。归档时怎样组织索引，会影响之后能否准确取回证据，因此保存与读取需要一起考虑。

这种比较限于机制，不能据此推断 Codex 使用了 MemexRL 的训练方法。

SWE-MeM 把压缩时机和范围也交给模型#

如果已经完成一轮排查，但 context 还没有接近上限，是否应该提前整理？如果只完成了其中一个子任务，是否可以只压缩对应的一段？

SWE-MeM 将压缩做成了可参数化的工具。模型给出当前分析、待压缩步骤的起止编号、替代摘要和剩余工作，系统据此替换选中区间。

其工具形式是：

compress(
    analysis,
    start_step_number,
    end_step_number,
    content,
    remaining_work
)

这让模型可以根据任务阶段选择处理范围：已完成的探索可以收束成结论，仍然需要细节的部分继续保留。

图 4：几种上下文管理方式的机制对比。SWE-MeM 将时机与处理范围开放给模型选择；这张图解释操作差异，性能比较需要另看实验。来源：SWE-MeM，Figure 2。

训练上，SWE-MeM 结合课程式微调与 Memory-aware GRPO，联合优化记忆决策和软件工程任务表现。它关注的是何时、何处、如何压缩，而这几项判断都需要结合当前轨迹。

对 coding agent 而言，这个方向有意义的地方在于：上下文整理可以跟随子任务的完成发生。容量限制仍然存在，但任务进度也成为决策依据。

CompactionRL 让摘要质量由后续任务检验#

CompactionRL 保留了摘要压缩，并把任务执行与摘要生成共同纳入 PPO 训练。

一次 rollout 跨越压缩边界之后，前面生成的摘要会影响后面的行为。训练需要处理跨边界的反馈，以及不同轨迹分段带来的损失权重问题。它采用 token 层面的损失归一化和跨轨迹的 GAE，连接执行与摘要的训练信号。

这里与 SWE-MeM 有一个明确区别：CompactionRL 的实验仍按固定剩余预算触发压缩，主要优化摘要及其后的执行。

一个有意思的观察是，纳入摘要训练之后，摘要变得更长、更详细。优化后的模型选择保留更多可用于后续行动的信息。

图 5：GLM-4.5-Air 设置下的摘要长度变化。蓝色圆点为 CompactionRL，浅蓝三角为不训练摘要的版本；前者的摘要长度随训练总体增加。这一子图呈现长度变化，摘要的任务价值仍需结合消融结果判断。来源：CompactionRL，Figure 4(a)。

这提醒我们，压缩率只是一个局部指标。少写几百 token，如果导致后面重新探索、重复测试，整体成本可能更高。摘要质量需要结合后续执行来判断。

放在一起看#

工作 记忆操作 训练关注点 主要边界
MemexRL 归档、索引、按索引读取 保存与读回如何配合任务执行 有效策略依赖可用的索引与存储
SWE-MeM 选择区间并替换为摘要 何时、何处、如何压缩 决策基于具体任务轨迹
CompactionRL 生成摘要并继续执行 摘要对后续任务的作用 实验触发阈值仍固定

这几篇工作把上下文管理的不同部分放进了优化目标。它们也说明，“模型学会管理上下文”需要拆成具体能力讨论，不能仅凭模型调用过一个记忆工具，就认为整套策略已经得到验证。

Harness 与模型需要怎样协同#

前面的讨论，主要围绕模型应该做哪些决策。但策略能否发挥作用，也取决于接口提供了什么保证。

ARC 可以作为系统侧的参照。它把工具观察结果写入追加式存储，通过稳定 ID 寻址。压缩时，确定性程序将较长的旧观察替换为引用，模型需要时按地址读回；这个压缩过程不调用摘要模型。

ARC 的可恢复性针对已归档的观察结果。它提供了回到证据的机制，模型是否选择正确地址仍需要单独判断。

这个区分也适用于更一般的 agent memory 设计：

  • 机制是否可靠。 写入是否成功，引用是否稳定，读回是否完整，截断有没有明确标记；
  • 策略是否有效。 模型是否保存了有用状态，能否发现信息缺口，是否选择了正确证据。

两者需要分别评估。否则，一次恢复失败，很难判断应该改工具接口、存储实现，还是模型的使用策略。

从工程角度看，我更关心下面几项结果：

维度 需要观察的问题
任务完成 跨窗口之后，最终任务是否仍能完成
约束保持 之前确认的要求、限制是否在后续执行中丢失
重复探索 是否重试已经失败的方案，是否重复执行已有结果的查询
证据恢复 能否找回关键原文，需要多少次调用
总体成本 写笔记、压缩、搜索、读回及任务执行的总 token 和耗时

这些是评测设计建议，具体比较还需要控制任务、模型和预算条件。活动窗口缩短，可以减少当次输入，但不能直接推出端到端成本下降。记忆管理本身也要消耗资源。

沿着这条线看，未来 harness 的一项重要工作，是把上下文操作做成可靠、可组合、可观察的接口；模型则通过任务反馈，学习怎样使用这些接口。

因此，所谓上下文管理能力的“内化”，可以落到一个具体含义：把一部分原本由外部规则决定的上下文选择，纳入模型可训练的行动策略。 存储、执行、预算边界与恢复机制，仍然由系统提供。

这也构成了两组相互关联的问题：系统能否让历史证据持续可用，模型能否在有限预算下选出当前任务真正需要的上下文。前者决定恢复的条件，后者决定这些条件能否转化为任务表现。
