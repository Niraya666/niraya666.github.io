When Agents Start Managing Their Own Context

From Codex context resets and history retrieval to MemexRL, SWE-MeM, and CompactionRL: how context management becomes a trainable agent policy.

中文版

In its GPT-6 Astra announcement, OpenAI highlighted a change to context management in Codex: the model can keep notes across context windows, while earlier windows remain searchable. Even if a requirement or test result was left out of the notes, it can still be recovered from past messages and tool outputs. Official announcement

There are two different questions here.

The first concerns the mechanism: where history lives, how it leaves the active window, and which interfaces can bring it back. The second concerns the policy: when to reorganize context, what to preserve, and when to look something up.

This article starts with Codex’s TokenBudget path and how it separates context resets, notes, and history queries. It then turns to MemexRL, SWE-MeM, and CompactionRL to examine how context management enters model training.

My view is that context management is becoming part of the agent policy. The harness provides executable memory operations. The model helps decide how to use them, shaping what it will see on its next call.

Distinguishing Context, History, and Working State#

When discussing compaction, it is easy to conflate “the model cannot see this right now” with “this information is gone.”

We need to distinguish at least three layers:

Layer What it stores How it is used
Active context Instructions, messages, and tool results for the current call Passed directly to the model
History Session messages, tool outputs, and events retained by the system Requires an interface for querying or recovery
Working state Summaries, notes, pending tasks, decisions, and evidence references Helps restore progress and locate details to examine

A tool output removed from context may still exist in the session record. But without an access interface, or without knowing what to query, the model will struggle to use that record in subsequent decisions.

Context management therefore involves both capacity and access. We need to limit the size of the active input while retaining usable routes to information outside the window.

The agent harness sits at this junction. It organizes requests, executes tools, persists state, and constructs the next model input. A common approach has been for the harness to decide when compaction is needed, then ask a model to produce a summary.

How Summary-Based Compaction Rebuilds the Input#

The OpenAI Cookbook’s SummarizingSession provides a clear example. Once the number of real user turns exceeds a threshold, it summarizes older history while preserving a number of recent turns verbatim. Cookbook example

At the message level, older history is replaced with a synthetic pair: a user message requesting a summary and an assistant message containing it. The next input looks roughly like this:

Regular instructions and request configuration
+ user: synthetic summary request
+ assistant: history summary
+ Last N complete turns, including tool calls and results
+ New input

The model already participates in context management here, but its main responsibility is the summary’s content. The program still determines when to trigger compaction, which history to process, how many recent messages to retain, and how to reassemble the input.

Compaction also exists at the API level. The Responses API’s /responses/compact returns a set of context items for subsequent requests. These include an opaque, encrypted compaction item and may retain other input items. This compressed state should not be equated with a human-readable summary. Compaction documentation

So “compact” names an operation that can have different implementations. Comparing approaches requires examining both the resulting input structure and how removed content can be accessed.

A Summary Can Preserve Progress While Omitting the Basis for a Decision#

Consider a hypothetical CSV import bug.

After investigating, the agent finds that a byte order mark (BOM) at the start of the file interferes with matching the first column name. It also tries a fix that does not work. At the context boundary, the summary says only: “Working on the CSV import bug. Initial investigation complete. Continue checking the encoding.”

This preserves the general direction. But the next model call may need other details:

  • How exactly the BOM appeared in the original output.
  • Which fix was already attempted, and why it failed.
  • Which test results support the current diagnosis.

If these details are absent from the summary and there is no other recovery path, the model may repeat the investigation—or repeat the same failed fix.

The difficulty is that whether information is worth preserving often depends on what comes next. An error message that seems incidental now may become decisive in the next step. A fluent summary that covers the main progress does not necessarily contain enough information to continue the task.

Repeated Compaction in a Codex Retrospective#

This risk has also appeared in evaluations. In the compaction-frequency section of Ghosts in the Codex Machine, dated October 31, 2025, Tibo and the Codex team wrote:

Evals confirmed that performance degrades with the number of /compact or auto-compactions used within a single session.

The team found that a growing share of sessions used compaction, while evaluations showed worse performance as the number of compactions within a session increased. The subsequent improvements included avoiding recursive summarization across repeated compactions and reminding users to keep sessions focused. Original report

The cumulative effect deserves attention. Mechanically, if the next handoff depends on the previous summary, that summary becomes the input to another round of information selection. Once a reason for failure is omitted early on, later rounds may continue without it.

Continuing after one compaction shows that a handoff occurred. Preserving working state must be tested through task performance across repeated context transitions. Evaluations should check whether constraints disappear and whether the agent revisits approaches that already failed.

This observation concerns the Codex implementation at that time. The report also discusses hardware, tool behavior, and timeouts; it does not attribute the overall degradation to a single factor. Its proposed improvements also include changes to the summarization mechanism itself.

Following this line of inquiry, we need to test two properties separately: whether information can be recovered, and whether the agent recovers it when needed.

Codex’s TokenBudget Path#

The relevant pull requests show Codex separating several responsibilities previously grouped under compaction into independent operations.

new_context Lets the Model Request a Context Reset#

PR #27488 introduced a model-facing new_context tool behind the TokenBudget feature flag.

Its execution flow can be summarized as follows:

The model calls new_context
→ Record the reset request
→ Consume the request after the current sampling phase ends
→ Rebuild the initial context
→ Continue the same task turn in a fresh window

This path does not generate a handoff summary or automatically reload the old session history into the new window. It gives the model another option: when the current window no longer seems suitable for continuing the work, it can request a reset.

Later, PR #29743 connected compaction under TokenBudget to a similar reset path. It starts a new window with the standard injected context, skipping the request for the server to summarize the old history.

The scope matters: this describes the TokenBudget path. Other configurations, models, and compaction entry points need to be examined separately.

notes Preserves Working State; history Provides a Route Back to Evidence#

How does the task continue after a reset?

PR #39827 introduced two groups of model-facing tools:

Tool Operations Suitable contents
notes Write, append, read, and search persistent notes Current objective, decisions, pending tasks, and evidence locations
history List windows and entries, search content, and read entries Original information from earlier messages and tool outputs

The division is fairly clear. Notes helps the model quickly recover its working state; history lets it check original material when needed. Notes can stay compact while detailed logs are retrieved through queries.

The earlier CSV example could follow this sequence:

Window A
Investigate the problem
→ Write notes with progress and pending tasks
→ Call new_context

Window B
Read notes
→ Decide that the earlier failure needs to be checked
→ Search and read history
→ Continue the fix using the original output

Figure 2: If both the summary and the notes omit the BOM detail, history offers another chance to read the original log. This is an illustrative flow; successful recovery depends on the model’s actual choices. Labels in this diagram are in Chinese.

These tools operate through the Codex backend. The implementation that introduced them requires the relevant configuration to be enabled, the OpenAI provider, and backend authentication.

Mechanically, the system provides a foundation for continuing tasks across windows. But writing notes and querying history both require the model to act. A reset does not guarantee that notes have been prepared, and searchable records do not guarantee that the model will find the right entry.

Original evidence is more accessible. How to use it remains a policy question.

From Memory Tools to Memory Policies#

Does giving an agent notes and history mean it knows how to manage context?

Tools define the available actions. The model still needs to judge when those actions are useful.

More specifically:

  • When to reorganize. Has the current subtask ended? Is there still value in retaining the full exploration process?
  • What to preserve. Which conclusions are stable, which hypotheses remain unverified, and which reasons for failure need to carry into the next stage?
  • When to retrieve. Does the current state support the next action, or should the model first check the original output?

These choices directly affect the rest of the task. Resetting too early can interrupt an unfinished investigation. Waiting too long can leave the context full of obsolete hypotheses. Notes that are too short raise recovery costs; notes that grow through endless appends become another long context.

The trigger for retrieval is particularly easy to overlook. If a note says only “continue checking the encoding,” how does the model in the new window realize that it is missing an important record of failure?

This is why working notes need to preserve unresolved questions and evidence locations. Alongside conclusions, they need clues that can prompt subsequent action.

Within the agent loop, task actions and memory actions now participate in the same decision process:

Current context + task progress + budget information
                         ↓
              The model chooses an action
                ↙                    ↘
     Read code, run tests     Write notes, retrieve,
                              compact, reset context
                ↘                    ↙
       The harness executes and builds the next input
                         ↓
                  Continue the task

This introduces a training question: how should a memory action be evaluated?

When the model records why an attempt failed, we do not yet know how many redundant attempts it will prevent. Likewise, an index is difficult to evaluate in isolation. Its value becomes apparent when a later model call actually needs the material it points to.

Memory operations therefore have delayed benefits. Learning these policies requires connecting later task outcomes to earlier memory decisions.

Training Context Management#

MemexRL Jointly Optimizes Storing and Reading Experience#

Memex(RL) uses Indexed Experience Memory: compact summaries and indexes remain in the window, while detailed material moves to external storage.

It provides two key operations:

  • CompressExperience: organize a summary and archive detailed material under indexes.
  • ReadExperience: retrieve the corresponding content by index.
Current working context
→ CompressExperience
→ Keep an indexed summary in the window; archive details externally
→ A later task step needs a piece of evidence
→ ReadExperience
→ The original material re-enters the context

MemexRL then uses GRPO-style reinforcement learning to jointly optimize task actions and memory reads and writes. Its reward combines task success with penalties for exceeding the context budget, redundancy, and formatting problems.

The paper also tracks changes in memory-tool use during training: compression calls generally decrease, while retrieval calls generally increase. At least in these experiments, training changes how the model stores and retrieves information.

Figure 3: Changes in memory-tool use during MemexRL training. Compression calls are shown above, retrieval calls below. Both plots come from the same training experiment, with Rollout Step on the horizontal axis. Call counts alone do not establish task quality. Source: Memex(RL), Figure 5.

This has a similar mechanical structure to notes/history: compact state retains a route back to detailed material. How indexes are organized during archiving affects whether evidence can later be retrieved accurately. Storage and retrieval therefore need to be considered together.

The comparison is limited to mechanisms. It does not establish that Codex uses MemexRL’s training method.

SWE-MeM Lets the Model Choose When and What to Compress#

If an investigation is complete but the context is still well below its limit, should the agent reorganize it early? If only one subtask is finished, can it compress just that portion?

SWE-MeM turns compression into a parameterized tool. The model supplies its current analysis, the starting and ending step numbers, a replacement summary, and the remaining work. The system then replaces the selected span.

The tool takes this form:

compress(
    analysis,
    start_step_number,
    end_step_number,
    content,
    remaining_work
)

This lets the model choose a span based on the stage of the task. Completed exploration can be condensed into conclusions, while material whose details are still needed remains intact.

Figure 4: Mechanisms for several context-management approaches. SWE-MeM lets the model choose the timing and span. This diagram explains operational differences; performance comparisons require the experimental results. Source: SWE-MeM, Figure 2.

For training, SWE-MeM combines curriculum-based fine-tuning with Memory-aware GRPO, jointly optimizing memory decisions and software-engineering task performance. It focuses on when, where, and how to compress, all of which depend on the current trajectory.

For coding agents, the useful implication is that context reorganization can follow subtask completion. Capacity limits still apply, but task progress also becomes a basis for the decision.

CompactionRL Evaluates Summaries Through Subsequent Task Performance#

CompactionRL retains summary-based compaction and jointly trains task execution and summary generation with PPO.

When a rollout crosses a compaction boundary, the earlier summary affects later behavior. Training must handle feedback across that boundary, as well as loss weighting across trajectory segments. CompactionRL uses token-level loss normalization and cross-trajectory GAE to connect the training signals for execution and summarization.

There is a clear distinction from SWE-MeM: CompactionRL’s experiments still trigger compaction at a fixed remaining-budget threshold. The main optimization targets are the summary and subsequent execution.

One interesting observation is that including summary generation in training produces longer, more detailed summaries. The optimized model chooses to retain more information that can support later actions.

Summary length generally increases with training in the former. This panel shows length changes; the summaries’ task value still needs to be assessed alongside the ablation results. This is a reminder that compression ratio is only a local metric. Saving a few hundred tokens may increase overall cost if it forces the agent to repeat exploration or tests later. Summary quality needs to be judged through subsequent execution.

Comparing the Approaches#

Work Memory operations Training focus Main boundary
MemexRL Archive, index, and retrieve by index How storage and retrieval support task execution together Effective policies depend on usable indexes and storage
SWE-MeM Select a span and replace it with a summary When, where, and how to compress Decisions depend on the specific task trajectory
CompactionRL Generate a summary and continue execution The summary’s effect on subsequent work The experimental trigger threshold remains fixed

These papers place different parts of context management inside the optimization objective. They also show why “the model has learned to manage context” needs to be broken down into specific capabilities. Calling a memory tool does not, by itself, validate the entire policy.

How the Harness and Model Need to Work Together#

So far, the discussion has focused mainly on which decisions the model should make. Whether a policy works also depends on what the interfaces guarantee.

ARC offers a reference from the systems side. It writes tool observations to an append-only store and addresses them with stable IDs. During compaction, a deterministic procedure replaces long, older observations with references. The model can retrieve them by address when needed. This compaction process does not call a summarization model.

ARC’s recoverability applies to archived observations. It provides a mechanism for returning to evidence; whether the model chooses the right address is a separate question.

This distinction applies to agent memory design more generally:

  • Is the mechanism reliable? Did the write succeed? Are references stable? Is retrieved content complete? Is truncation explicitly marked?
  • Is the policy effective? Did the model preserve useful state? Can it detect an information gap? Does it choose the right evidence?

These need separate evaluations. Otherwise, when recovery fails, it is difficult to tell whether the tool interface, storage implementation, or the model’s usage policy needs to change.

From an engineering perspective, I care more about the following outcomes:

Dimension What to examine
Task completion Can the agent still finish the task after crossing context windows?
Constraint retention Do previously confirmed requirements or limits disappear during later execution?
Repeated exploration Does the agent retry failed approaches or repeat queries whose results already exist?
Evidence recovery Can it retrieve the key original material, and how many calls does that take?
Total cost Total tokens and elapsed time for note-taking, compaction, search, retrieval, and task execution

These are suggestions for evaluation design. Actual comparisons still need controlled tasks, models, and budgets. A shorter active window can reduce the current input, but it does not establish lower end-to-end cost. Memory management consumes resources too.

Following this direction, an important job for future harnesses is to expose context operations through reliable, composable, and observable interfaces. Models can then learn to use those interfaces through task feedback.

“Internalizing” context-management ability thus has a concrete meaning: moving some context choices previously determined by external rules into the model’s trainable action policy. Storage, execution, budget boundaries, and recovery mechanisms remain responsibilities of the system.

This leaves two connected questions: can the system keep historical evidence available, and can the model select the context the current task actually needs within a limited budget? The first establishes the conditions for recovery. The second determines whether those conditions translate into task performance.
